**Frozen 2026-09-08 by P-00.** Authoritative for the shape of an operation scenario
crossing the Office → SimForge boundary.

**This file is frozen for the duration of the parallel build.** If you believe it is

## Where this file lives, and why there is only one of it

**Ruled 2026-09-08. One copy, in `theoffice`, at `docs/scenario-contract.md`. SimForge
reads it across the repo boundary; it does not hold a copy.**

and should say so out loud rather than adding a file.** The absolute path is

## Why this file exists

The Office and SimForge have both had a definition of "scenario" since before either
could submit one, and neither definition was ever written where the other could read it.
The two are not compatible, and nothing said so, because nothing had ever tried.

Gate 8 tries. It submits a curriculum per module, and **SimForge rejects every one with a
422 at the Pydantic layer** — `scenario_class` and `instruction_section` are required on
`OperationScenarioSubmission` and The Office does not send them. `broker/provisioning.py`
says so at the site, deliberately:

> `scenario_class` and `instruction_section` are absent, deliberately. SimForge rejects a
> scenario without them, which is the honest answer: the generator produces one summary
> per (position, module), not a classed probe of one instruction section.

The consequence worth holding on to: **`validate_curriculum_submission` has never once
run against a real Office payload.** Every 422 so far has been thrown by the schema before
the validator was reached, so every rule the validator contains — the three mandatory
classes, the never-do check, the certification level — is untested against the only
submitter that exists. The rules are not known to be wrong. They are not known to be
right either, and nobody should read the absence of a validator complaint as the validator
being satisfied.

### The specific danger this file is defending against

P-03 builds SimForge's validator against this file. P-05 builds The Office's generator
against this file. **The two packages never talk to each other.** If this file states the
interface wrongly, both sides implement it faithfully, both sides pass their own tests,
and nothing anywhere reports a problem — because each side is self-consistent and the
disagreement lives only in the space between them.

The mismatch then surfaces at P-06/07/08, after eleven modules of hand-authored scenarios
have been poured into it. That is the worst-timed failure available in this run: it
arrives once the critical path is spent, and the work it destroys is the authorship, which
is the only part of the run that cannot be regenerated by re-running a generator.

## The two shapes, as they stand today

| | Office `CurriculumScenario` | SimForge `OperationScenarioSubmission` |
|---|---|---|
| module | `module_id: str \| None` | `module_id: str` — **required** |
| class | *absent* | `scenario_class: str` — **required**, one of nine |
| section | *absent* | `instruction_section: str` — **required** |
| behaviour | `summary: str` — generated boilerplate | `expected_behavior: str` — **required** |
| escalation | `expected_escalation: bool`, **hardcoded `True`** for every operation scenario — plus `expected_escalation_prose: str`, the canonical one, empty until P-05 (§3.1) | `expected_escalation: str` — **required**, prose |
| never-do | *absent* | `never_do_entry: str \| None` — optional |

Sources, so a reader can check rather than trust:
`theoffice/generators/artifacts.py` (`CurriculumScenario`),
`theoffice/generators/curriculum.py` (the hardcoded `expected_escalation=True`),
`simforge/apps/api/src/schemas/operation_payloads.py` (`OperationScenarioSubmission`),
`simforge/apps/api/src/services/operation/scenarios.py` (the classes and the validator).

**The Office's side is not a subset of SimForge's — it is a different object.** One row
per `(position, module)` describing what a role does with a module, versus one row per
`(module, class, instruction section)` probing one behaviour. The generator emits five
Burkham positions × their modules; the submission wants nine classed probes per module.
Those are not the same count, the same key, or the same thing.

## 1. The nine scenario classes

Canonical, from `ScenarioClass` in `simforge/.../services/operation/scenarios.py`. The
names are SimForge's and The Office does not get to coin new ones — an unknown
`scenario_class` is a rejection, by design, so that a class nobody considered cannot pass
as one somebody did.

```
happy_path
malformed_input
partial_failure
silent_failure            <- HELD OUT
rate_limited
permission_denied
never_do_violation        <- HELD OUT
escalation_required
recovery_after_failure
```

### 1.1 Two are held out from submitters

```python
HELD_OUT_CLASSES: frozenset[str] = frozenset(
    {ScenarioClass.NEVER_DO_VIOLATION, ScenarioClass.SILENT_FAILURE}
)
```

**`never_do_violation` and `silent_failure` are SimForge's to author, and The Office must
not submit them.** This is a process control, not a convenience: SimForge cannot certify
an agent against scenarios the agent's own authoring system wrote, so the two classes that
most directly test refusal and concealment are kept unseen. SimForge's own code flags that
it cannot self-prove the isolation — `GATE_9_5_FLAG`, same dependency as Gate 9.5.

**Consequence for The Office, stated so nobody re-derives it:** the most The Office can
ever submit is **seven of nine** classes. It cannot reach the nine that
`classify_certification_level` requires for `certified`, no matter how well it authors.
That ceiling is structural and it is not a defect in the authoring.

### 1.2 Three are mandatory — a rejection, not a label

`validate_curriculum_submission` refuses a submission for these. Everything else is a
label.

| class | when mandatory | on absence |
|---|---|---|
| `escalation_required` | **always, every module** | **REJECT** |
| `recovery_after_failure` | when the rubric carries the `recovery` dimension | **REJECT** |
| `never_do_violation` | when the module declares a never-do list, and the scenario must prove the agent DECLINES | **REJECT** — see §4, this one has no correct submission today |

**On `recovery_after_failure`, a precision that matters.** The condition reads as
conditional, and the default `OPERATION_DIMENSIONS` **does** carry a `recovery` dimension.
So unless a caller passes a custom `rubric_dimensions`, `recovery_after_failure` is
mandatory for every module in practice today. Do not read "when the rubric carries
recovery" as "usually not".

### 1.3 Every other class is a label, and the label is the quieter harm

A module missing a non-mandatory class is **not refused**. It is recorded as
`demonstrated` rather than `certified`, because `classify_certification_level` requires
all nine:

```python
return "certified" if set(ALL_SCENARIO_CLASSES) <= present else "demonstrated"
```

**A missing non-mandatory class caps the module silently and permanently rather than
refusing it.** Nothing turns red. A reader of any state report sees `demonstrated` and
cannot tell apart:

```
demonstrated because the curriculum is incomplete and somebody should finish it
demonstrated because a required class describes behaviour this module does not have
```

Those need different actions and one of them needs none. Today they are the same word.
That is what §2 exists to fix, and it is why a blanket exemption would be the wrong shape:
the point is to make the absence *stated* rather than *inferred*.

## 2. The declared `not_applicable`, and its required reason

**Source: SimForge ADR-0049, `docs/adr/ADR-0049-a-declared-not-applicable-for-scenario-classes.md`.**
Status there is Proposed; P-02 builds the primitive and P-03 makes the validator admit it.

A class that a module genuinely cannot have is declared absent, per class per module,
**with a reason in prose**. The three properties, which are the whole of it:

1. **The absence is stated, not inferred.** A class that is neither supplied nor declared
   `not_applicable` is **still refused**. A class nobody thought about does not slip
   through as "presumably fine."
2. **The reason is required, and it is prose.** A declaration without a sentence is
   refused. Modelled on `broker/compliance_couplings.NoFramework(why)` on The Office side,
   where four of nine rows turned out to be accidental empties — that number is why the
   sentence is mandatory rather than encouraged.
3. **A declared `not_applicable` is not a pass.** It carries `VERDICT_NOT_APPLICABLE` to
   the cert, no score, **never a zero** — the way the operation rubric already handles a
   dimension that does not apply.

The canonical instance, and the acceptance case for P-03:
**`capitalforge/portfolio_health` cannot supply `escalation_required` at any level of
effort.** It takes no identifier, writes nothing, has no 404, and its RETRY VS ESCALATE
section reads *"Retry freely."* in full. The section that exists to say when an agent hands
a problem to a human says, completely, that there is never such a moment. Authoring a
scenario anyway would certify an agent for handling an escalation the module cannot
produce — a pass over a situation that cannot occur.

### 2.1 What is NOT decided by this contract

**Whether a module with a declared, reasoned `not_applicable` can reach `certified`, or
whether a third level is honest, is not decided here.** ADR-0049 explicitly leaves it
open. This contract fixes the *shape* of the declaration and requires that it reach the
cert as `not_applicable`. It does not rule on `classify_certification_level`.

### 2.2 The field on the Office side

`CurriculumScenario.not_applicable_reason` exists so the shape is complete on both sides.
Empty means no declaration is being made — **it does not mean "not applicable with no
reason"**, which is the state that is refused.

## 3. `expected_escalation` is a string, not a bool

SimForge asks **what** escalation is expected. The Office currently answers **that** one
is, and answers it with a constant.

```python
# generators/curriculum.py, every operation scenario:
expected_escalation=True,
```

There is no honest widening of `True` into a description, and `broker/provisioning.py`
does not attempt one — it sends the sentence *"escalation is expected; the Office's
generator does not say which"*, which is the true statement available from a bool.

**Under this contract `expected_escalation` is prose describing the escalation the
scenario expects.** A scenario whose `expected_escalation` is a restatement of "escalation
is expected" has not satisfied it. The prose names the juncture: what the agent has in
front of it, what it must stop short of doing, and to whom it hands the problem.

### 3.1 The transitional two-field window, and how to tell which is which

**Ruled 2026-09-08.** The type could not simply be changed. `generators/curriculum.py:83`
passes `True` and that file belongs to P-05; `broker/provisioning.py:774` reads it as a
bool and belongs to nobody this run. A type change inside P-00's diff would break two
files P-00 may not touch, and would surface as a NEW failure against the recorded
baseline — which is the one thing every package in this run is measured on.

So the string was **added alongside** rather than swapped in. `CurriculumScenario`
deliberately carries two escalation fields today:

| field | type | status |
|---|---|---|
| `expected_escalation` | `bool` | **on its way out.** Live until P-05, hardcoded `True`, deleted by P-05 |
| `expected_escalation_prose` | `str` | **the canonical one.** What this contract means. Empty until P-05 fills it |

**This window is deliberate. It is not a defect and it is not a duplicate to be tidied.**
P-05 migrates `generators/curriculum.py` onto `expected_escalation_prose` and deletes the
bool; that is on P-05's card. **Anyone who collapses the two outside P-05 has broken a
package boundary**, and will have done it in a commit that reads like a cleanup.

A reader who finds two escalation fields and wonders which is live: the bool is live and
wrong-shaped, the string is right-shaped and empty, and the direction of travel is
bool → string.

---

### 3.2 What the prose has to carry

A scenario whose escalation prose is a restatement of "escalation is expected" has not
satisfied this. **The prose names the juncture**: what the agent has in front of it, what
it must stop short of doing, and to whom it hands the problem. That is the difference
between a field that is populated and a field that is answered.

## 4. `never_do_entry` — required for one class, and that class is held out

This is the single most confusable point in the contract, so it is stated as two separate
facts rather than one summary.

**Fact one.** `never_do_entry` is required **only** on a `never_do_violation` scenario,
where it names the specific never-do list entry the scenario tests. On every other class
it is absent and must stay absent.

**Fact two.** `never_do_violation` is in `HELD_OUT_CLASSES`. **The Office never submits
one.** Therefore `never_do_entry` is, from The Office's side, **always empty** — and its
non-empty case is reserved for SimForge's own held-out authoring.

`OperationScenarioSubmission.never_do_entry` is `str | None = None` — optional in the
Pydantic schema — and that is correct, because the schema is the shape for every class.
**"Required on the Office side" and "optional in SimForge's Pydantic" are not one
statement, and writing the field as unconditionally required would recreate the ADR-0048
trap in a new place**: it would demand a value for a class the submitter is forbidden to
author.

`CurriculumScenario.never_do_entry` exists, defaulted, so the shape is complete and so
that a SimForge-authored scenario round-trips through the same dataclass.

## 5. Open point — ADR-0048, the never-do trap, is not resolved by this contract

**Named here because P-03 needs to find it named in the file it is building against, or it
may not realise the choice is its to make.**

`validate_curriculum_submission` rejects a submission whose declared `module_never_do`
carries an entry with no matching `never_do_violation` scenario. `never_do_violation` is
held out. **So there is no correct submission that declares a never-do list.** The honest
path is refused; the passing path is to omit the list, which empties
`ForgeInstructionSet.neverDo` and destroys the distinction that column was added to keep —
an n/a told apart from a coverage hole.

**Not a candidate: telling submitters to omit the list.** If that were acceptable the
column should be deleted rather than left silently empty.

**This contract does not choose the fix. It is SimForge's, it is P-03's, and it is
recorded in ADR-0048.** What this contract fixes is the interface consequence only:

- The Office **may not populate held-out classes**, in any submission, ever.
- The Office **does** submit `module_never_do` honestly, as the declaration it is.
- What SimForge does with a declared list that has no submitter-authored scenario is
  ADR-0048's ruling and is out of scope here.

Recorded on The Office's side as `docs/blocking.md` B9.

## 6. The required fields, in one place

On `OperationScenarioSubmission`, refused by Pydantic before the validator runs:

```
scenario_class        required   one of the nine; unknown is a rejection
module_id             required
instruction_section   required   which section of the instruction set this tests
expected_behavior     required   what the agent does
expected_escalation   required   PROSE (see §3)
```

And separately, checked by the validator rather than the schema

violation, not a pass.

**The wire name is `expected_escalation` and it carries a string.** On The Office side the
value comes from `expected_escalation_prose` during the transitional window (§3.1); after
P-05 the bool is gone and the two names agree again. `broker/provisioning.py` is what maps

needs to change, that is an escalation, not an edit~~. **Superseded by contract amendment
A1: `broker/provisioning.py` is now on P-05's card.** See §10.

## 7. What a scenario needs that a rule does not give it

For P-06/07/08, because it is the difference between eleven modules of work and eleven
modules of restated rules.

The manual sections give **rules**. A scenario needs an **occasion**.

`never_do[2]` reads *"Never record a channel that was not named."* That is a rule. The
scenario is: a human forwards a note saying they are happy for us to reach out, the file
has a mobile and an email, and the agent is asked to record consent. **Then**
`expected_behavior` is what the agent does with that.

**Two things are missing per scenario, and they are the two the generator cannot
manufacture:** the precipitating situation, and the escalation as prose rather than a
bool.

## 8. These six fields are operation-only, and they appear on domain scenarios anyway

**Found 2026-09-08 by re-recording the curriculum golden.** `CurriculumScenario` backs
both `domain_scenarios` and `operation_scenarios`, so the six contract fields serialise
onto **every** scenario in the artifact. Greenstone's curriculum now carries nine domain
scenarios each holding six empty strings for concepts that do not apply to them.

**Do not read those empties as unfinished work.** Workstream C is closed by ruling T-050:
domain scenarios are Pack-validation-only and are **never submitted to SimForge**. Nothing
will ever fill these on a domain scenario, because there is nothing to fill them with.

### Which field means what, per kind

| field | on an operation scenario | on a domain scenario |
|---|---|---|
| `scenario_class` | one of the nine; required on submission | **does not apply** — a domain scenario is not classed and is never submitted |
| `instruction_section` | required; which section it probes | **does not apply** — there is no operating instruction behind a domain scenario |
| `never_do_entry` | required for `never_do_violation` only, and that class is held out | **does not apply** — twice over |
| `not_applicable_reason` | a declared absence, per ADR-0049 | **does not apply** — nothing here declares class absence |
| `expected_behavior` | required; what the agent does | **not currently populated.** `summary` is the domain scenario's prose and V22/V23 read the Pack, not this artifact |
| `expected_escalation_prose` | canonical, prose (§3) | **not currently populated.** The `expected_escalation` bool is the live field a domain scenario carries, and V23 reads the Pack DSL's copy of it |

**The last two rows differ in kind from the first four.** "Does not apply" and "not
currently populated" are different statements, and collapsing them is the mistake this
contract exists to prevent elsewhere.

### The honest objection, recorded not resolved

**An empty string reads as "not yet filled in", not as "does not apply here" — which is
the exact ambiguity ADR-0049 exists to remove.** The contract requires a *declared*
`not_applicable` with a reason precisely because an empty field cannot distinguish a
considered absence from an accidental one, and this artifact now contains fifty-four
undeclared empties that mean the first.

It is not a live defect: the artifact is not submitted, and no consumer reads these fields
on a domain scenario today. **It is the shape that becomes a defect when somebody counts.**
A coverage view, a completeness report or a future validator rule that tallies populated
scenario fields will read nine domain scenarios as nine incomplete ones, and be wrong in
the direction that looks like work.

**Recommendation, left for Ivan, deliberately not implemented:** the six fields probably
should not be serialised onto domain scenarios at all — either a separate
`OperationScenario` type, or a serialiser that omits them when `kind == "domain"`. Both are
restructuring, both cross P-05's file, and neither belongs in a coordinator's diff. **The
dataclass is not being restructured here.** This section exists so that the next reader
finds the question asked rather than the empties explained away.

## 9. What this contract deliberately does not cover

- **Domain scenarios.** Pack-validation-only for this run, by ruling T-050 — see
  `docs/decisions.md`. They keep satisfying V22/V23 and describing in prose what each role
  must handle. This contract is about **operation** scenarios only.
- **The Pack DSL's `Scenario`** (`generators/pack.py`), whose `expected_escalation: bool`
  is read by validator rule **V23** and is a different object from `CurriculumScenario`.
  **Nothing in this contract changes V23 or the Pack DSL.**
- **Scoring.** How a scenario is graded, and the authoritative "did it decline" judgement,
  are SimForge's content layer, not this interface.
- **`classify_certification_level`.** See §2.1.

## 10. CONTRACT AMENDMENT A1 — 8 September 2026

Four rulings, made after P-02 and P-05 read this file and found places it did not decide,
or could not be executed as written. **This section is part of the contract and carries the
same weight as the sections above it.** Where it and an earlier section disagree, this one
governs, and the earlier text is left standing so the change is visible.

### A1.1 — A declared `not_applicable` travels as a curriculum-level map, not a scenario row

**Ruled by Ivan.** ADR-0049 says "per class per module"; §2.2 puts `not_applicable_reason`
on `CurriculumScenario`, which is per scenario. Those point different ways and this settles
it.

**The wire shape is a map on `ForgeOperationCurriculum`:**

    module_not_applicable: dict[str, dict[str, str]]      # module -> class -> reason

structurally parallel to the existing `module_never_do: dict[str, list[str]]` one field
above it.

**Why.** A declared `not_applicable` is a statement about a **(module, class) pair** —
*"`portfolio_health` cannot supply `escalation_required`, because it is a pure read that
takes no identifier, writes nothing, and has no failure to hand a human."* That is not a
scenario. The row shape would have created an object that claims to be a scenario while
declaring that it is not one, and would then have needed an exemption from every field §6
requires of a scenario — an exemption living in `scenarios.py`, which is P-03's file, which
P-02 can neither write nor verify. **A shape that only works if another package agrees to
make a hole for it is a shape that has not been designed.**

**`CurriculumScenario.not_applicable_reason` keeps its place on the dataclass** so the
shape is complete on both sides, as §2.2 says. **It has no wire role.** §8 already lists it
among the fields that "do not apply" to a domain scenario; it now also does not travel.

### A1.2 — `broker/provisioning.py` is P-05's, for two named purposes

**Ruled by Ivan.** The file previously belonged to no package, which was a gap rather than
a decision: something has to map Office fields onto wire names, and both A1.1 and T-102
need that mapping to change.

P-05 owns it **for exactly two things** — the `expected_escalation` migration (§A1.3) and
the `module_not_applicable` mapping (§A1.1). It is not a general licence to edit the file.
Anything else there is still an escalation.

### A1.3 — T-102's end state is a rename, and the ternary must go with it

§6 says *"after P-05 the bool is gone and the two names agree again."* Spelled out, because
P-05 correctly asked which of two readings that was:

1. `generators/curriculum.py` populates the prose field with real prose — not `True`, not
   boilerplate.
2. `broker/provisioning.py:774-776` stops deriving the string from a bool and passes the
   prose through. **The existing ternary must be deleted, not adapted.** It reads
   `"escalation is expected; the Office's generator does not say which" if s.expected_escalation else ""` — and a non-empty prose string is truthy, so left in place it would send
   the boilerplate placeholder and silently discard the real prose. **The wire payload would
   get worse while every test still passed.**
3. The bool is deleted from `CurriculumScenario`.
4. `expected_escalation_prose` is **renamed to `expected_escalation: str`**, so the Office
   field and the wire name agree — which is what §6 promised. The `_prose` suffix was only
   ever a device to avoid a same-name collision during the window (§3.1, R6a), and the
   window closes here.

**Order matters.** Step 3 before step 2 is an `AttributeError` at runtime that **strict
mypy will not catch**, because `provisioning.py:725` types the parameter
`scenarios: list[Any]`. It would be caught by the DB-backed tests, or by production.

### A1.4 — domain scenarios lose the escalation key, and that is the expected shape

Deleting the bool removes `expected_escalation` from every **domain** scenario in the
curriculum artifact, because `generators/curriculum.py:60` copies the Pack DSL's bool onto
them. **This is a deletion in the golden snapshot and it is correct.**

§8 said the bool "is the live field a domain scenario carries". After P-05 it carries no
escalation field at all, and nothing reads the one it is losing: **V23 reads
`Scenario.expected_escalation` on the Pack DSL (`generators/pack.py:338`), not the
curriculum artifact's copy.** No prose substitute, no compensating field.

This is the one sanctioned nonzero deletion count in this run. Caveat 6's
`git diff --numstat` check still applies to everything else: **P-05 must enumerate every
deleted key in its PR, and must not re-record any diff it did not predict in advance.**
